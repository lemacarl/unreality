# Contributing

## Workflow
- Branches: `feat/<issue#>-<slug>`, `fix/<issue#>-<slug>`, `chore/<slug>`, `docs/<slug>`, `spike/<slug>` (throwaway prototypes, never merged; ADRs land via `docs/` or `chore/` branches).
- Commits: conventional commits (`feat:`, `fix:`, `docs:`, `chore:`, `test:`).
- PRs: title `<type>: <summary> (#<issue>)`, body has `Closes #<issue>`, how it was tested, open concerns. Squash-merged after CI is green and independent review approves. Never push to `main` directly.
- Docs and CHANGELOG are updated in the same PR as the change.
- No new dependency without an ADR. Never weaken tests or lint to pass CI.
- Public repo: no personal data, screenshots of your screen, or secrets in issues, PRs or logs.

## Local development
Build commands are in the [README](README.md#build-and-run). Layout: `Sources/UnrealityCore` (pure logic), `Sources/UnrealityPlatform` (OS integrations), `Tests/`, and the app shell in `App/` described by `project.yml`.

- `Unreality.xcodeproj` is generated by XcodeGen and gitignored. Edit `project.yml`, then run `xcodegen generate`; never hand-edit or commit the project.
- Dev builds must use a stable signing identity and bundle ID, or macOS drops Screen Recording/Camera/Accessibility grants on every rebuild. Signing comes from `Config/Signing.xcconfig`, which signs ad hoc (`CODE_SIGN_IDENTITY = -`) so a clean checkout builds without an Apple Developer team. Ad-hoc signatures change on every build, so for permission work copy `Config/Local.xcconfig.example` to `Config/Local.xcconfig` (gitignored, pulled in by `#include?`), uncomment and set your `DEVELOPMENT_TEAM` and `CODE_SIGN_IDENTITY = Apple Development`; no `xcodegen generate` regenerate is needed, because xcconfigs are read at build time. Do not change signing in Xcode's Signing & Capabilities: that edit lives in the generated project and is lost on the next `xcodegen generate`. Never commit team IDs. Keep the bundle ID `com.lemacarl.unreality`.
- Hardened runtime is enabled, but ad-hoc Debug builds are signed without it, so a missing hardened-runtime entitlement (for example `com.apple.security.device.camera` for camera access) only shows up in Release builds or builds signed with a real identity. Test permission work in one of those.
- Secrets live in the Keychain only.

## Lint rules
Two custom SwiftLint rules in `.swiftlint.yml` keep the core free of OS frameworks. They are a regex-based guard; CI backs them with a compiler check and an escape-hatch check (see [CI](#ci)).

- `core_no_os_imports`: files in `Sources/UnrealityCore` may import only Foundation, Dispatch, Observation, Synchronization, RegexBuilder and GRDB (storage, ADR 0002).
- `core_tests_no_os_imports`: files in `Tests/UnrealityCoreTests` may import the same modules plus UnrealityCore and Testing.

GRDB is not allowed in `Tests/UnrealityCoreTests`: tests use the core's storage API on in-memory databases. Both are allow-lists. They ignore comments and strings, and catch attributed, access-level, scoped and backticked imports (`@preconcurrency import X`, `internal import X`, `public import X`, `import struct X.Y`, ``import `X` ``) as well as an import after other code on the same line. Known residual of the regex (contrived): a comment between `import` and the module name (`import /* c */ AppKit`); the CI compiler check catches it. New core dependencies must be added to the list in the same PR as their ADR.

Do not switch the rules off. CI fails on a nested `.swiftlint.yml`/`.swiftlint.yaml` anywhere in the repo, on a `swiftlint:disable` (including `:next`, `:this`, `:previous`) naming either rule in any `*.swift` file under `Sources`, `Tests` or `App`, and on `swiftlint:disable all` or `custom_rules` in the core or its tests.

To check the rules after editing them, run `scripts/ci/selftest.sh`. It copies the repo to a temporary folder, injects probe files (for example `@preconcurrency import AVFoundation`, `internal import AVFoundation`, `import struct Foundation.Data` and `import GRDB` in `Sources/UnrealityCore` and `Tests/UnrealityCoreTests`) and confirms each guard flags the violations and passes the allowed forms (`import GRDB` is clean in the core but flagged in its tests).

## Manual checks
Some behaviour cannot run in CI. Run these locally when a PR carries the `needs-manual-test` label for them, and say in the PR that you did.

- **Keychain secret store (#14).** `UNREALITY_KEYCHAIN_TESTS=1 swift test --filter KeychainSecretStoreIntegrationTests` runs the `SecretStore` contract against your login keychain. Without the variable the suite is skipped (the default, and in CI). It uses a throwaway service `com.lemacarl.unreality.tests.<UUID>` and deletes every item it creates, so it never reads or changes the app's real items. Expect 3 passing tests and no keychain prompt. Afterwards, `security find-generic-password -s com.lemacarl.unreality.tests` should report that no item was found (or open Keychain Access and search for `unreality.tests`). Never paste real secrets into test output, issues or PRs.
- **Pause hotkey (#15).** Launch the app (a signed or ad-hoc Debug build), make another app frontmost and press Control-Option-Command-P: the menu-bar icon switches between `eye` and `eye.slash`, and the popover agrees; press again to switch back. The popover shows "Shortcut: ⌃⌥⌘P", and no Accessibility or Input Monitoring prompt appears. The "could not be registered" caption appears only when macOS refuses the registration (for example a duplicate registration within this app); a combination held by another app is not detected and simply may not reach Unreality, so do not test for that.
- **Settings window (#13).** Launch the app, open the popover and click "Settings…" (or press Cmd-, while the popover is open): the Settings window comes to the front with General, Capture, Privacy and AI tabs. General shows the pause shortcut "⌃⌥⌘P" read-only. Change the idle threshold (Capture) and both retention steppers (Privacy); steppers stop at their limits (1–60 minutes, 1–24 hours, 1–365 days). Quit from the popover, relaunch and reopen Settings: the changed values are still there. `defaults read com.lemacarl.unreality` lists only `idleThresholdMinutes`, `rawCaptureRetentionHours` and `contentRetentionDays` (plus any keys macOS itself adds, such as window frames) as plain numbers. `defaults delete com.lemacarl.unreality` restores the defaults (5, 24, 30) on the next launch.
- **Launch at login (#56).** Needs a build signed with a real identity (an Apple Development certificate is enough; `Config/Local.xcconfig` with your team, see [Local development](#local-development)) copied to `/Applications` and launched from there: `SMAppService` ties the login item to the app's location and signature, so ad-hoc or unsigned builds, or a copy run from DerivedData, may report "not found", fail to register (the General tab then shows the error code), or leave stale entries that point at an old build. Remove stale entries in System Settings > General > Login Items. To inspect what macOS has recorded, use the read-only `sfltool dumpbtm` first; `sfltool resetbtm` resets all background-item records for every app and needs a restart, so use it only on a test machine. Steps: (1) first launch: Settings > General shows "Open Unreality at login" off, and Unreality is not listed in Login Items; (2) turn it on: Unreality appears under "Open at Login" in System Settings > General > Login Items (macOS may also show a "Login item added" notification); (3) log out and back in: the menu-bar icon appears without launching the app by hand; (4) turn the toggle off: the entry disappears from Login Items, and after the next log-in the app does not start; (5) approval: with it on, remove Unreality from the "Open at Login" list in Login Items with the minus (-) button instead (the switches under "Allow in the Background" are for background items, not this entry), then return by clicking the still-open Settings window so the app becomes active: if macOS reports approval is needed, the tab says so and "Open Login Items Settings…" opens that pane; if macOS reports it as off, the toggle shows off. Either way the toggle matches System Settings after the app becomes active again; (6) `defaults read com.lemacarl.unreality` shows no login-item key (macOS, not settings, holds the state).

- **Activity source and Accessibility (#17).** Needs a human: Accessibility can only be granted in System Settings. Run from a terminal app (not Finder): `UNREALITY_ACTIVITY_TESTS=1 swift test --filter WorkspaceActivitySourceIntegrationTests`. It makes Finder frontmost, then opens two new Finder windows on empty temporary folders (`unreality-ax-test-...`, deleted afterwards; close the two windows yourself), then switches back. It prints only counts (trust, samples, Finder samples with a title, Finder title changes, all title changes), never titles. Run it twice: (1) with your terminal app **not** allowed in System Settings > Privacy & Security > Accessibility: expect `Accessibility trusted: false`, `Finder samples with a title: 0`, `all title changes: 0`, a pass, and no permission prompt; (2) after allowing the terminal app there (remove it again afterwards if you do not want it): expect `Accessibility trusted: true`, `Finder samples with a title` of at least 1 and `Finder title changes` of at least 1 (the AXObserver path), and a pass; the test asserts these. The test runner's grant belongs to the terminal app, not to Unreality. The app itself does not start the source yet; once it does, repeat with the app's own grant and check that pausing (menu bar or hotkey) stops title reads and that Unreality's own windows never produce titles.

- **Browser URLs and Automation (#19).** Needs a human: the Automation prompt can only be answered by a person, per browser. Use throwaway browsing (a neutral page such as `https://example.com/?q=test`), never real accounts. Open the browsers you want to check (Safari, Chrome, Brave, Edge, Arc, Firefox; each with a normal window in front) and run from a terminal app: `UNREALITY_BROWSER_TESTS=1 swift test --filter BrowserURLProviderIntegrationTests`. It prints, per running known browser, the permission state and the reading kind, never the URL. (1) Before any grant: expect `permission notDetermined` and `unreadable(automationNotDetermined)` for Safari and Chrome-family browsers, `unreadable(unsupportedBrowser)` for Firefox, a pass, and **no prompt**. (2) Run with `UNREALITY_BROWSER_TESTS=prompt`: macOS asks once per undecided browser whether the terminal app may control it. Allow one browser and deny another: expect `permission granted` and `url (not shown)` for the allowed one, `permission denied` and `unreadable(automationDenied)` for the denied one, and a pass. A URL is read only when the window's scripted name matches its Accessibility title, so for steps that expect `url (not shown)` your terminal app also needs Accessibility (see the #17 check); without it, expect `AX title read: false` and no URL. (3) Private windows, one per browser you have, each brought to the front of its browser before running with `=1` again: Chrome incognito, Arc incognito, Edge InPrivate, Brave private window and Brave private window with Tor. Expect `unreadable(privateWindow)` (or `unreadable(failed)` if the browser reports no mode) for each, never `url (not shown)`; record the results in the PR, since the Arc, Edge and Brave rows in docs/PRIVACY.md stay unverified until then. For Safari, a private window is expected to read as `url (not shown)` (a documented limit, #72). (4) Safari with its Settings window, or the Downloads window, in front: expect `unreadable(noWindow)` or `unreadable(failed)`, never `url (not shown)`. (5) Never launches: note which browsers are running, quit one, run with `=1` and confirm that the quit browser is not listed and stays quit (nothing reopens it) for a minute afterwards. (6) Hardened runtime: build the app signed with a real identity (`Config/Local.xcconfig`, see Local development), then check with `codesign -d --entitlements - <path to Unreality.app>` that it has `com.apple.security.automation.apple-events`. Once the source is wired into the app, also confirm that the Automation prompt shows the Unreality reason text and that a URL is read under the hardened runtime; ad-hoc Debug builds are not hardened, so they do not prove this. The grants belong to the terminal app, not Unreality: reset them afterwards with `tccutil reset AppleEvents <terminal bundle ID>` or in System Settings > Privacy & Security > Automation. The app does not start the source yet; once it does, repeat with the app's own grant (the prompt should show the Unreality reason text).

CI reads the pins (and the release-asset SHA-256 digests) from `scripts/ci/tool-versions.env` and fails if this table, `swiftlint_version` in `.swiftlint.yml` (SwiftLint also refuses to run with a different version) or the installed tools disagree with it. `project.yml` enforces `minimumXcodeGenVersion`, which must not exceed the pin. To bump a tool, change all of these in one PR. GRDB is the only runtime dependency; bump it deliberately in its own PR and re-check health (CI checks that the table, `Package.swift` and `Package.resolved` agree).

## CI
`.github/workflows/ci.yml` runs on every pull request, on pushes to `main` and on manual dispatch. It has one job whose status check is named **`ci`**: make `ci` the required status check in the branch protection rule for `main`. It uses no secrets, only read access to the repository contents, and builds unsigned (`CODE_SIGNING_ALLOWED=NO`); signing and notarisation are out of scope.

Runner: the `macos-26` image (arm64) with Xcode selected explicitly from the Tool versions table (`/Applications/Xcode_<version>.app`). XcodeGen and SwiftLint are downloaded from their GitHub releases at the pinned versions and checked against SHA-256 digests. Third-party actions are pinned to commit SHAs. SwiftPM dependency checkouts are cached, keyed on the Xcode version and `Package.swift`/`Package.resolved`.

Steps, in order; any failure fails `ci`:

1. Tool versions: `scripts/ci/check-tool-versions.sh` (see Tool versions).
2. SwiftLint escape hatches: `scripts/ci/check-lint-escape-hatches.sh` (see Lint rules).
3. Bundle ID: `scripts/ci/check-bundle-id.sh` checks that `AppIdentity.bundleIdentifier` matches `PRODUCT_BUNDLE_IDENTIFIER` in `project.yml` (and, after the app build, the built `Info.plist`).
4. `swiftlint lint --strict`.
5. `swift build` and `swift test`.
6. Core import backstop: `scripts/ci/check-core-imports.py` asks the compiler (`-scan-dependencies` for direct imports, `-emit-loaded-module-trace` for loaded modules) what `UnrealityCore` imports in debug and release conditions, and fails on anything a probe importing only the allow-list (read from `core_no_os_imports`) does not. Unlike the regex it sees through comments and `#if`, and it catches modules such as IOKit that Foundation already loads transitively, or raw `SQLite3`/`GRDBSQLite` next to GRDB. Package modules on the allow-list (GRDB) are resolved from SwiftPM's build output, so it runs after `swift build`. Its compiler flags mirror SwiftPM's by hand: if `Package.swift` gives `UnrealityCore` `swiftSettings`, mirror them in the script.
7. Guard self-test: `scripts/ci/selftest.sh` proves the guards still catch injected violations (also after `swift build`, for GRDB).
8. `xcodegen generate` and `xcodebuild build` of the `Unreality` scheme.

Every step is a plain shell command; run the scripts locally the same way before pushing (with the pinned tools on `PATH`).

## Agents and models
| Role | Model | Effort | Used for |
|---|---|---|---|
| PM | Claude Sonnet 5.5 | Medium | Planning, issues, docs, merge decisions |
| Builder | Claude Opus 5.5 | Medium | Implementation, spike prototypes |
| Reviewer | Claude Opus 5.5 | High | Code, functional, privacy/security reviews (fresh context, never the PR's builder) |
| Researcher | Claude Sonnet 5.5 | Medium | Research for ADRs; gathers evidence, does not decide |

Builder, Reviewer and Researcher are defined in `.claude/agents/`; the PM is the main orchestrating session.
