# Privacy

Target behaviour (implemented so far: Keychain storage of the API key (#14), local SQLite storage (#16), the global pause hotkey (#15), settings (#13), the frontmost app / window title source (#17), browser URL capture for known browsers (#19; neither is wired into the app or storage yet) the privacy filter that drops excluded apps and sites before storage (#20) and launch at login (#56); no capture is recorded yet. This document is updated with every capture-related change).

Storage: one SQLite file, `~/Library/Application Support/com.lemacarl.unreality/unreality.sqlite`. Every open makes the folder owner-only (0700) and the database, `-wal` and `-shm` files owner-only (0600). SQLite `secure_delete` is on, so deleted pages are zeroed in the database file once checkpointed; the write-ahead log (`unreality.sqlite-wal`) may still hold old page images until it is truncated (automatic PASSIVE checkpoints do not), so the retention deletes run `wal_checkpoint(TRUNCATE)` after purging. Retention deletes only events that ended strictly before the cutoff and never deletes open sessions. The app is not sandboxed: like any non-sandboxed app's files, other processes running as the same macOS user can read the database. Time Machine backups and APFS local snapshots may hold copies that retention and delete-all cannot reach. Schema: [ARCHITECTURE.md](ARCHITECTURE.md#storage).

Settings (#13): non-secret preferences only (idle threshold and retention windows so far, as plain numbers) in the app's UserDefaults domain, `~/Library/Preferences/com.lemacarl.unreality.plist`. They hold no captured data and never secrets (the settings value type does not admit them; the API key stays in the Keychain). The retention values are placeholders: nothing is captured or deleted by them yet.

Launch at login (#56): off by default. Unreality registers itself as a login item (`SMAppService.mainApp`) only when the user turns on "Open Unreality at login" in Settings > General, never silently at first launch. macOS keeps that state (System Settings > General > Login Items, where the user can also remove it); Unreality does not store a copy. Started at login, Unreality behaves exactly as when launched by hand, and its menu-bar icon shows that it is running.

Defaults: password managers, messaging and mail apps, and password-manager, messaging, webmail and banking sites excluded (implemented in #20; list and limits in [Privacy filter](#privacy-filter)); global pause hotkey (Control-Option-Command-P by default; implemented in #15 via Carbon `RegisterEventHotKey`, which needs no Accessibility or Input Monitoring permission and only reports that one combination, never other keystrokes. If another app or a system shortcut holds the same combination, macOS does not tell Unreality, and pressing it may do nothing; always check the menu-bar icon, which is the source of truth for whether capture is paused); visible capture indicator; API key stored in the macOS Keychain only (implemented in #14: login keychain, not iCloud-synchronised, never logged; see ARCHITECTURE.md, "Secrets").

## Frontmost app and window titles (#17)
What is read, on the Mac, by `WorkspaceActivitySource`:

- **Frontmost app**: bundle ID (for example `com.apple.finder`), localised app name and process ID, from `NSWorkspace` app-activation notifications. Needs no permission. The process ID is never meant to be stored.
- **Focused window title** of the frontmost app only, through the Accessibility API (`AXUIElement`): the app's focused-window attribute (a reference to the window) is queried, then that window's title attribute. Needs the **Accessibility** permission (System Settings > Privacy & Security > Accessibility). Window titles can contain sensitive text: document and file names, email subjects, chat contact names, web page titles, sometimes account names. Nothing else is read: no window contents, keystrokes or other UI elements. Unreality's own windows are excluded: no Accessibility call targets Unreality's own process, and its samples are app-only. Titles are also never read for a process without a bundle ID, because no exclusion list could match it.

When it is read: once when tracking starts or resumes, on every app switch, and when the frontmost app's focused window or its title changes (notifications, no polling). Nothing is read while capture is paused: the coordinator stops the source on pause and drops anything that still arrives.

Permission: Unreality checks whether it has Accessibility access without prompting (`AXIsProcessTrusted`) and exposes that state; the system prompt is shown only when the user asks for it (`requestAccess()`, for a future onboarding/settings button), never silently at launch. Without the permission, samples are app-only (no titles; nothing is recorded yet). Revoking it takes effect at the next app switch or title change. After granting it, titles start at the next app switch, or immediately when the app re-checks the permission (`refreshAccessibilityTrust()`, for example when it becomes active again).

Before a title is read, the privacy filter is asked whether that app's titles may be read at all, so excluded apps' titles are never read. This is per app: excluding a site or a private window inside a browser can only drop or redact the sample after its title (and URL) was read into memory (#19, #20), before anything is stored or passed on. That filter is `PrivacyFilter` (#20, see [Privacy filter](#privacy-filter)); samples are still not stored or shown anywhere, because the source is not yet wired into the app.

## Browser URLs (#19)
What is read, on the Mac, by `AppleEventBrowserURLProvider` for `WorkspaceActivitySource`:

- **The URL of the active tab of the frontmost browser's front window**, and nothing else: no page content, other tabs, history, bookmarks or form data. A short sequence of Apple Events reads it, all addressed to one window by its unique ID, so a window that comes to the front mid-sequence is never read:
  1. `id of window 1` (the front window). A front window that is not a browser window (Safari's Settings, say) or no window at all reads as "no window".
  2. Chrome family only: that window's `mode`. Only `normal` continues; an `incognito`, unknown or unreadable mode stops here, so a private window's name and URL are never read.
  3. That window's `name`, which must equal the focused window's title read through Accessibility. If it differs (an undocked DevTools window, a window switch in progress) or there is no title, the read stops: title and URL could belong to different windows, so both are dropped.
  4. The URL of that window's current tab (`URL of current tab` in Safari, `URL of active tab` in the Chrome family).

  The sequence stops at the first failure.
- **When**: only if the window-title policy allowed that browser's title (so never for excluded apps, without Accessibility permission, for Unreality itself, or while paused), and only for the known browsers below. It is read when the browser becomes frontmost and whenever its focused window or window title changes (a tab switch, or a navigation that changes the title). Not polled: a URL change that does not change the title is not seen until the next title change or app switch.
- The events go to the frontmost browser's process, so they never launch a browser. Each waits at most 0.25 s for an answer; after a timeout, that browser is sent nothing more until the next app switch, and none is sent while the browser is not answering Accessibility requests either. So a hung browser costs at most one timeout per activation; a responsive one costs a few milliseconds per read (three events for Safari, four for the Chrome family).
- The URL is the browser's own string, which the browser has already normalised. Nothing is parsed from window titles or the address bar.

**Automation permission.** macOS asks once per browser whether Unreality may control it (System Settings > Privacy & Security > Automation > Unreality; the prompt shows the reason from the app's `NSAppleEventsUsageDescription`). Reading never prompts: before sending anything, the provider checks the permission without asking (`AEDeterminePermissionToAutomateTarget` with `askUserIfNeeded: false`). A granted state is remembered for that browser process until the next app switch, or until an event reports a permission error (a grant revoked in System Settings). If the user has not decided yet or has denied it, nothing is sent, and the sample says so (`automationNotDetermined`, `automationDenied`). The prompt appears only through `requestAutomationPermission(for:)`, for an explicit user action (a future onboarding or settings button), and only while that browser is running. `automationPermission(for:)` reports the state without prompting, for a future settings UI. Denying it costs only that browser's titles and URLs (its samples become app-only); it can be changed in System Settings at any time.

**Browsers.** The source of truth is `KnownBrowser.all` in `Sources/UnrealityCore/BrowserURL.swift`. Bundle IDs are matched case-insensitively.

## What leaves the device
Only text built from the signals above (app/window titles, redacted URLs, OCR text, active/idle totals, presence totals) is sent to the Claude API for summaries, only after the user enables it and supplies a key. Images, webcam frames and excluded-app data are never sent. Excluded apps/sites are filtered before storage; screen capture must use ScreenCaptureKit app/window exclusion so excluded windows are not captured even when visible behind another app (tracked in #23).

## Privacy filter
The privacy filter (UnrealityCore, #20) sits between capture and storage, in two places:

1. **At capture**, `ActivityCoordinator` (#17) asks `PrivacyFilter` before reading any window title (and so any browser URL). `allowsWindowTitle(for:)` says no for excluded apps and for apps without a bundle ID, so their titles and URLs are never read. The coordinator then runs every sample through `filter(_:)`, which drops all samples from excluded apps (including app-only samples without a title) and from excluded sites, redacts browser URLs, and drops titles it cannot attribute (below). The coordinator itself also withholds titles and URLs without Accessibility permission, for processes without a bundle ID and for Unreality's own windows.
2. **Before storage**, the same `PrivacyFilter` instance turns a sample into a `FilteredEvent`. Its input is the sample (with its browser URL, if any) and the span's end. It applies `filter(_:)` again, so a sample that skipped the coordinator gets the same checks; filtering an already filtered sample changes nothing.

**What is guaranteed, and what depends on the caller.**
- *Redaction holds by construction.* The repository's only insert takes a `FilteredEvent`. Only the privacy rules (`PrivacyRules`, which `PrivacyFilter` wraps) can create one: its initialiser is private to the filter's file, and it is not `Decodable`. The stored-event type `ActivityEvent` cannot be inserted. So no URL reaches storage unredacted, and no process ID or app display name is stored (`FilteredEvent` has no field for them).
- *Exclusion depends on the caller.* Exclusion is only as good as the rules the event was built with. Any code can create `PrivacyRules` with an empty blocklist. So the pipeline must build events through the app's single `PrivacyFilter` instance, which holds the user's current rules, and never through a copy of the rules that could go stale after the blocklist changes.
- *Code inside the storage layer can bypass the type.* Code inside `UnrealityCore` with access to `DatabaseManager`'s internal database writer could still write rows directly (raw SQL, or GRDB's `updateAll` on records). That access is internal to the core and used only by the repository; reviews must keep it that way.

Unit tests run fixture activity from excluded apps and sites through the coordinator and the filter into a recording repository, an in-memory database and a database file. The fixtures include wrapped `blob:`/`view-source:` URLs and extension pages. The tests check that none of it, nor a sentinel in its titles, is stored or written to disk. Another test checks that the default list below matches the code.

**What it does:**
- **Excluded app** (frontmost app's bundle ID on the blocklist): titles never read, every sample dropped, no event.
- **App without a bundle ID**: titles never read; app-only event (no bundle ID, no title).
- **Excluded site**: the URL's host, or a parent domain of it, is on the blocklist. The sample is dropped (no event), so the window title is not stored either.
- **Known browser without a readable URL** (#19, see [Browser URLs](#browser-urls-19)): the sample is kept app-only, without its title. A `nil` URL on a sample means only "not a web sample" (not a known browser, or its title was not allowed); a known browser with no URL reading at all is treated as unreadable.
- **Wrapped URLs** (`blob:`, `view-source:`, `filesystem:`, for example a bank statement opened as `blob:https://secure.bank.example/<id>`): the inner URL's site is checked. If allowed, the event is stored as the wrapper plus the redacted inner URL. `blob:` and `filesystem:` keep only the inner origin.
- **Browser-internal password, payment and wallet pages** (`chrome://password-manager`, `edge://wallet`, `brave://wallet`, and `settings` pages whose path mentions passwords, passkeys, autofill, payments, addresses, personal info or a wallet, such as `chrome://settings/passwords` or Edge's `edge://settings/personalinfo`, on the `chrome`, `chromium`, `edge`, `brave`, `arc`, `vivaldi` and `opera` schemes; and Firefox's `about:logins`): always dropped, also when wrapped in `view-source:`.
- **Browser-extension pages** (`chrome-extension://`, `safari-web-extension://`, `safari-extension://`, `moz-extension://`, `extension://`, `edge-extension://`, `opera-extension://`, `ms-browser-extension://`): always dropped. Their host is an extension ID, not a site, and they include password managers' full-page vaults.
- **URLs that cannot be checked**: no event, because the filter fails closed rather than store a title it could not attribute. This covers:
  - unparseable URLs and URLs without a scheme;
  - URLs without a host, such as `https:///path`, `file:///…` (local files opened in a browser), `javascript:` and `mailto:`, except for two allowed host-less schemes: `about:` (browser-internal pages) and `data:` (inline content). Those two are stored as the scheme only, **without the window title**: an `about:blank` or `data:` pop-up (a bank's print or statement window, say) takes its title from the page that opened it, which cannot be checked;
  - URLs with a `\` before the query or fragment. Browsers and Foundation disagree on where such a URL's host is (a browser reads `https://chase.com\@evil.com/` as host `chase.com`, Foundation as `evil.com`), so the filter does not guess. Browsers report normalised URLs, which have none there.
- **Other URLs.** `http(s)` URLs keep only `scheme://host[:port]/path`. The query, fragment, `user:password@` credentials and `;` path parameters (such as `;jsessionid=`) are dropped, rather than the whole URL being blanked. The host is stored in canonical form: percent escapes decoded, lowercase, with internationalised names as punycode. A host whose escapes do not decode, or that decodes to a character no host can contain (for example `/`, `@`, a space or NUL), cannot be checked and drops the event. A stricter mode (`hostOnly`) also drops the path. Other schemes that have a host (`ftp:`, `wss:`, `chrome://settings`) are checked against the blocklist by host and stored as `scheme://host` only (no credentials, port, path, query or fragment).
- **Idle spans** are stored without app, title or URL.

**Blocklist.**
- Bundle ID entries are matched case-insensitively. An entry matches exactly or, ending in `.*`, the prefix and everything under it (`com.example.*`). Any other `*`, including a bare `*`, makes the entry invalid, and it is ignored.
- A domain entry matches that host and all its subdomains (`example.com` matches `www.example.com`, not `notexample.com`). A scheme, user info, path, port, `*.` or leading dot in an entry is ignored. Entries and hosts are compared in one canonical form: percent escapes decoded (`ch%61se.com` is `chase.com`, as in a browser), then lowercase punycode, so `bücher.de` and `xn--bcher-kva.de` are the same entry. IPv6 addresses go in brackets (`[::1]`) and are not decoded, so zone IDs stay as they are. An entry with a `*` anywhere but a leading `*.` (`*`, `com.*`, `a.*.b`) is invalid and ignored. So is an entry with a single label (`com`, `localhost`, or `*.com`, which would otherwise exclude a whole top-level domain).
- User entries extend the defaults (`Blocklist.defaults.union(user)`). The settings UI that collects and persists them, and lets users remove a default, comes in M6.

**Limits.** The filter only sees what capture sources report about the frontmost app and its active tab:
- **Only the active tab's URL is checked.** An excluded site is recognised only from the URL of the frontmost browser window's active tab. It is not recognised in a background tab, another window, a non-browser app (an embedded web view, a mail preview), or when it appears only in a window title.
- **Unknown browsers keep their titles.** Only the browsers listed under [Browser URLs](#browser-urls-19) are recognised. Any other browser, or a browser whose bundle ID changed, is treated as an ordinary app: its window titles (page titles) are kept and no site is checked. Add it to the blocklist to exclude it.
- **Safari private windows are not detected.** Safari's scripting interface does not say whether a window is private, so a private window's URL and title are read and treated like any other (excluded sites are still dropped). Chrome-family private (incognito) windows are detected and never read; their samples are app-only.
- **Firefox loses titles.** Firefox, and the other browsers without URL support, give app-only samples: time is kept, titles and sites are not.
- **URL changes without a title change are missed** until the next title change or app switch, because the URL is read on those notifications (no polling). The previous URL, already checked, stays attributed until then. Likewise, a read that only fails intermittently (a timeout) with an unchanged title is not treated as a change: the sample already emitted stays in force.
- **Private-window detection in Arc, Edge and Brave is unverified** until the manual checks in CONTRIBUTING.md have been run for each; an unexpected window mode fails closed.
- **Titles and URLs are read into memory before the site check.** For a browser that is not excluded as an app, the title and URL of an excluded site are read and then dropped by the filter before anything is passed on or stored.
- **Domains, not paths.** Domain rules cannot match paths, so direct messages on general sites (`instagram.com/direct`, `x.com/messages`, `linkedin.com/messaging`, `facebook.com/messages`) are not excluded by default.
- **Kept paths can contain secrets.** With the default `keepPath` mode, URL paths are stored, and they can contain password-reset tokens, magic-link codes, invite codes or share IDs (`/reset/<token>`). Use the `hostOnly` mode to store only the site.
- **IP-literal entries are not normalised.** `[0:0:0:0:0:0:0:1]` does not match `[::1]`, and `0x7f.1` does not match `127.0.0.1`. Browsers report the canonical form, so enter IP addresses that way.
- **Titles are not checked.** Window titles of allowed apps are stored as they are and may mention excluded services, such as a document named after a bank. Titles are not matched against the blocklist.
- **Defaults are best effort.** Bundle IDs change between app versions, and new apps appear. Banking is mostly done in the browser, so the defaults cover some large banks and payment services by domain and no banking apps: add your own bank's app and site.
- **The filter decides what is stored, not what is captured.** Screenshots of excluded windows must be avoided at capture time with ScreenCaptureKit exclusion (#23).
- **No retroactive deletion.** Adding an entry does not remove data stored before it was added.
- **Excluded-app time may be misattributed.** Time spent in an excluded app may currently be counted as time in the app used before it. Its samples are dropped, so the step that builds spans from samples cannot tell when the previous app's span ended. That will hold until #21 adds an anonymous boundary marker for excluded activity.

**Logging.** Window titles and URLs are never logged. `ActivitySample`, `BrowserURLReading`, `FilteredEvent` and `ActivityEvent` redact the window title (and URL) in `description`, `debugDescription`, string interpolation and `dump`, so logging one by mistake does not leak them; the internal parsed-URL type does the same. GRDB's `publicStatementArguments` stays off: it is set explicitly, and a test checks that a database error does not contain the inserted title. So SQLite error messages never carry stored values.
